# The viewer refetches on an interval only while the Realtime channel isn't confirmed healthy, and not at all once the case has ended

The viewer's only live-update path is a Supabase Broadcast ping over a websocket, and the query it drives is configured with `staleTime: Infinity` and `refetchOnWindowFocus: false` (ADR `0006`: Realtime is a doorbell, the DB is the source of truth). Broadcast is fire-and-forget with no replay, so a ping sent while the viewer's socket is still connecting or reconnecting is lost forever and the viewer stays stale until the next broadcast or a manual reload. We tried to fix this twice before: `9002cbf` added a blind 5-second `refetchInterval` for every viewer, and `7130789` then removed it, arguing that with an awaited, acknowledged publish the broadcast is the delivery mechanism and a manual reload is an acceptable escape hatch.

We have now re-introduced a fallback refetch, but narrowly scoped: the viewer refetches the viewer state on a 5-second interval **only while the Realtime channel has not confirmed `SUBSCRIBED`** (still connecting, `TIMED_OUT`, `CLOSED`, or `CHANNEL_ERROR`), and stops as soon as it reaches `SUBSCRIBED`. The refetch additionally stops once the case is ended, since nothing can change after that; the viewer learns about the end through exactly the same channels (broadcast ping, or a fallback refetch returning `ended: true`), then the interval switches off. The refetch reads the same viewer endpoint the query already uses, so ADR `0006`'s single-source-of-truth invariant is preserved: the interval is just a second, HTTP-based doorbell, never a source of row data.

This reverses `7130789`'s "a manual reload suffices" stance, and deliberately. That stance was written from a single-device default; the product premise is one shared, read-only room device that the students are not allowed to touch, and the cockpit is expected to control the viewer completely. A mid-case un-release correction semantically *must* reach the room even if the ping for it is lost, and asking the room to reload defeats the live-teaching premise.

Consequences and rejected alternatives:

- **Rate limiting stays comfortable.** A stuck-unhealthy viewer polls at ~12 requests/min against the `viewer:read` limiter (300/min/IP), leaving ample headroom for several stuck devices behind one classroom NAT.
- **No background refetch.** The room device is on and focused on its single tab at all times, so `refetchIntervalInBackground` is left off; a briefly-backgrounded tab may go stale silently, which is accepted.
- **True long polling rejected.** We considered a held viewer request with server-side change detection (long polling proper, per the issue's original title). Rejected: with refetch-as-source-of-truth there is no server-side state to hold, it adds a held endpoint and a second rate-limit surface, and a serverless-held request trades requests for invocation time for no benefit at this volume.
- **Always-on blind interval refetch rejected.** Refetching every viewer every 5 seconds regardless of socket health reintroduces the churn `7130789` removed, pressures the per-IP rate limit under classroom NAT, and masks broadcast degradation behind constant successful polls.
- **Server-side websocket subscription for change detection rejected** by the existing precedent already recorded in the broadcast publish path: a websocket held open from a Vercel serverless function gets frozen after the response flushes.
