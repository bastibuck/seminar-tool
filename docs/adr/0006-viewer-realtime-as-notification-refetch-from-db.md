# The viewer treats Realtime events as notifications and refetches from the DB as source of truth

The viewer only ever reads case state through `GET /api/viewer/:code`: React Query holds the query key, and both Realtime subscriptions in `app/viewer/[code]/viewer-realtime.tsx` (`releases` on `*`, `cases` on UPDATE) are parameter-less callbacks that just call `queryClient.invalidateQueries(...)`. The websocket message is a ping — a signal that something changed — never a source of row data. The delivered `payload.new` / `payload.old` fields are ignored in production code.

We chose this deliberately over reading the payload directly. A payload is a point-in-time snapshot of whatever the event happened to carry; the DB is authoritative and always current. Doing a refetch on every event keeps a single source of truth (the tables) and sidesteps the question of which fields an event did or did not include. The cost is a REST round-trip per event, which is fine at this app's volume (a handful of releases per hour per case).

Two consequences follow:

- **`replica identity full` is load-bearing — keep it** on both Realtime tables. Although no production code reads `payload.old` or `payload.new`, the subscriptions in `viewer-realtime.tsx` filter on `case_id=eq.<id>`. Realtime routes a change to a subscription by evaluating the filter, and for a DELETE the only columns available for that evaluation come from the pre-image in `payload.old`. With `default` identity the pre-image carries only the primary key, so a DELETE cannot be matched to its `case_id` and is not delivered. With `replica identity full` the pre-image includes `case_id`, so the un-release DELETE reaches the case-scoped subscription and triggers the refetch. (Verified empirically: with `default` identity an unfiltered subscription receives the DELETE but the `case_id`-filtered one does not; switching to `full` restores delivery.) So the DELETE-driven invalidation depends on `replica identity full`; the only pay-off of `default` would be marginally smaller WAL writes, which is not worth breaking un-release propagation. Integration tests assert the DELETE arrives (INSERT/UPDATE also assert on `payload.new`, populated regardless of identity).
- **RLS does not gate this decision.** Whether RLS ends up on (`#20`) or off, the DELETE still needs `case_id` in its pre-image for the case-scoped filter to route it, so the replica-identity posture (`replica identity full`) does not depend on the RLS outcome. The dependency noted earlier that put `#18` behind `#20` was about what DELETE payloads *carry* for clients to read; since the viewer never reads payloads and only needs routing, the two tickets are independent.

Alternatives rejected: reading `payload.new` directly to render released findings (couples the UI snapshot to the event shape and to RLS/identity behavior, and risks staleness), and building the viewer feed purely from event aggregation (second source of truth alongside the tables).
