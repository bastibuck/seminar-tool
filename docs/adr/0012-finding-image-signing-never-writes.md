# Finding-image URL signing never writes to storage; placeholder provisioning is an explicit one-time backfill

Decided during the Finding-image module deepening (2026-09): `signFindingImages` is a read-seam operation — it mints signed URLs for released and admin-displayed Finding images — and must never touch storage for writing. Historically it lazily uploaded a placeholder SVG for any path ending in `placeholder.svg` (a seed/backfill-migration artifact), which put a storage write on every page-view GET of a legacy Finding, and one admin GET even minted a URL it then discarded. We moved provisioning off the read path into an explicit, idempotent `scripts/backfill-placeholder-images.ts` (run as `npm run db:backfill` after any `db reset` in dev, and once against production before this change deploys). Signing now filters to owning paths, mints URLs with the 10-minute TTL, and writes nothing.

Rejected alternative: keeping the lazy upload but hiding it behind a named internal seam. That preserved a write on the read seam, made "signing is read-only" untestable, and left the risk that any future rescue-on-missing-path would silently restore the write. The backfill is idempotent and deliberately lives outside the database lifecycle: storage uploads are not SQL, so a migration cannot provision them; a script is the honest home.

Consequences: placeholder paths stay signable (the path regex still accepts `placeholder.svg`) so legacy rows keep working; the read seam is pure and unit-testable against an in-memory storage adapter; the admin Finding GET no longer mints a URL it does not return.
